## 2026-11-20: Consultation: assigning sparse subjective ratings to EEG windows
**Asked:** Reviewer 2 (via my Google account, free tier, at her instruction to consult reviewers when unsure). Cross-check against docs/fatigueset-research.md and docs/literature.md before citing, an AI answer is a lead, not a source.
**Question:** FatigueSet records subjective ratings only 3× per session (M1 baseline, M2 post-physical, M3 post-cognitive). How do researchers assign those ratings as labels to EEG windows, and what are the leakage risks?

**Methods named:**
1. **Backward assignment**: windows before rating t(k) take rating t(k) (e.g. M3 applied to the preceding cognitive-task block). Reviewer 2's suggested starting point: simple, transparent.
2. **Forward / carry-forward**: windows after t(k) take rating t(k) until the next rating.
3. **Interpolation** (linear/spline/step) across M1–M3 onto window midpoints, continuous targets or binned classes.
4. **Stage/delta proxies**: protocol stage, activity tier, or Δ = M3 − M1 as coarse labels.
5. **Thresholded binarisation**: fixed cutoffs, per-session medians, or per-subject z-scores.

**Leakage risks named:**
- Overlapping windows in random splits share raw samples/artefacts → group by subject/session (LOSO/GroupKFold), temporal buffers within session.
- Interpolation = look-ahead: labels for early windows encode future ratings. Prefer causal/backward assignment for the primary pipeline.
- Thresholds/normalisation computed on full session/subject leak label distribution + baseline physiology → compute inside training folds only. (Matches our leakage discipline in PLAN.md §7.)
- Protocol/motion confounding: ratings pair with distinct phases (incl. treadmill) → model may learn motion/EMG, not fatigue. Check: can ACC/artefact features alone predict the labels?

**Status:** Input for the Week 1 label-rules decision (docs/label_rules.md). Decision itself still to be made + locked by me; literature anchors (MSARNet, FatigueSense block approaches) take precedence where they differ.

## Reviewer 3 review 44: independent code evaluation (21 Nov 2026)
A third evaluator, consulted for the first time on this project. It was given only the source bundle (all 48 Python files under src/), the README and the final code manifest (docs/code_manifest_final.md). The earlier reviews and their conclusions were deliberately withheld, so its reading of the code is independent of the panel record above. Verdict: conditionally supportive, not yet fully verified. It checked the manifest against the bundle and found all 48 files hash-identical to the recorded state. It confirmed the core leakage discipline in the code itself: in the baseline, imputation, scaling and class weights are fitted inside the training folds; the LOPO evaluation genuinely excludes the held-out participant; in the CNN, normalisation statistics and class weights come from the subtraining portion only; early stopping is driven by a carved validation set, never by the test fold; windows are four seconds and non-overlapping. It found no instance of the primary LOPO model training on held-out participant windows.
Major findings: (1) The bandpass filtering is zero-phase (sosfiltfilt) and therefore non-causal: each window's features are computed with access to samples later in the recording, so any claim must be restricted to retrospective, offline classification of recorded data. (2) cap_pool selects the test windows using the test labels before the folds are built (per-session M1 windows are capped to the retained M3 count), so the reported estimates are conditional on a label-balanced test pool rather than on the natural window population. (3) The CNN validation carve (src/models/cnn_segval.py, carve_validation) takes each run's label from its first window, which assumes every run is single-class; run_id is defined by timestamp gaps in preprocessing, not by block boundaries, and the code does not assert the assumption. (4) CNN reproducibility is not fully guaranteed: no deterministic-algorithms settings, GPU backend details unrecorded, and fold results are skipped when a metrics.csv already exists, with no hash validation of what produced it. (5) The primary FatigueSet cohort is outcome-selected: sessions enter the primary analysis only where the subjective fatigue rating rose (M3 above M1), which bounds the population the results describe.
Minor findings: (6) The within-participant and within-session normalisation variants are transductive (they use statistics from the data being scored) and must stay labelled as sensitivities. (7) The CNN input is not strictly raw EEG: the input tensor also carries two validity-indicator channels alongside the four EEG channels, so the README's description of the CNN input is incomplete. (8) The np.trapz compatibility alias (needed because the pinned NumPy removed np.trapz) is applied in some drivers and not others, inconsistently. (9) cap_pool re-instantiates its random generator per session with the same seed, which correlates the subsampling patterns across sessions.
What it could not verify: the numerical results. It was given no run artefacts, no data and no docs beyond the README and the manifest, so it could not check any headline number against stored outputs. It recommended inspecting the processed window index and the prediction files for a decisive audit.
My standing answers. F1: accepted as scope, not as a defect; this is an offline analysis of recorded data by design and no claim in the project is prospective. The retrospective scope belongs in the limitations; it is already carried in the limitations bank in substance, and the exact wording is mine to confirm. F2: the cap is a pre-registered balancing rule, fixed before any modelling, blind to outcomes and applied identically to every fold; the uncapped, class-weighted variant (V1) was run as a sensitivity and agrees with the primary (LOPO 0.503 [0.445, 0.552] against 0.508). The estimand qualification, that the estimates describe the capped pool, is accepted for the paper. F3: verified against the stored index on 21 Nov 2026. In data/processed/windows_a1_index.csv, the index cnn_segval.py loads and the stored canonical CNN window set (806 windows), there are 287 (participant, session, run_id) groups and none of them contains more than one distinct label; restricting to windows with labels 0/1 in M1/M3 blocks changes nothing, because every window in that index is an M1 or M3 window. In the uncapped parent pool (data/processed/windows_a1_uncapped_index.csv, 1,053 windows) there are 358 groups and again none is mixed. The missing assert is still a fair hardening note, but the first-window label is the run's only label in every run in the stored data. F4: accepted as a limitation; the CNN null is already reported as weak evidence, in part for the training-stability reasons recorded in reviews 31 to 34, and the environment pin exists at docs/environment_pin.md, which was not among the materials this reviewer was given. F5: the subjective-rise filter is the locked primary label rule, and RQ4 tested it directly: block-phase labels over all 36 sessions, with no rise filter, give LOPO 0.516 against the primary 0.508, so the filter does not drive the result; the population qualification stands and is already stated in the write-up. F6: accepted; both normalisation variants are labelled sensitivities wherever they appear and are never headline evidence. F7: accepted as a wording correction to the README's description of the CNN input, for me to approve. F8: on the primary paths the alias is applied, and the pinned environment and drivers are recorded in docs/environment_pin.md and docs/code_manifest_final.md; centralising it in one place is a fair engineering note and is recorded here. F9: accepted as a minor statistical note; the five cap seeds still produce different pools, the canonical pool is the seed-0 pool, and no reported result depends on the cap-seed choice.
